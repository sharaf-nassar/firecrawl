# Spec: mcp-capability-gaps

## Problem Statement

The local self-hosted Firecrawl stack exposes two MCP tools whose advertised capability does not match what the stack can actually do. Both gaps produce silent or late failures for the primary user of the local MCP (Claude Code sessions targeting `http://127.0.0.1:3002` via `scripts/local-firecrawl-mcp`).

**Gap 1 — `firecrawl_extract` is advertised but cannot succeed.** Code research corrected the initial premise: the extract worker IS running locally. `apps/api/src/harness.ts` (`startServices()`, ~lines 1177-1186) unconditionally spawns `node dist/src/services/extract-worker.js` inside the `api` container (`docker-compose.yaml:114` runs `node dist/src/harness.js --start-docker`), and the RabbitMQ topology (`extract.jobs` quorum queue, `extract.dlx` exchange, `extract.dlq` — `apps/api/src/services/extract-queue.ts:5-7`) is fully provisioned. The actual root cause is **missing LLM configuration**: all five model env vars (`OPENAI_API_KEY`, `OPENAI_BASE_URL`, `MODEL_NAME`, `MODEL_EMBEDDING_NAME`, `OLLAMA_BASE_URL`) are scaffolded as empty strings by `scripts/init-local-env.sh:83-88` and are empty in the live `.env`. `apps/api/src/lib/generic-ai.ts` selects OpenAI as default provider when `OLLAMA_BASE_URL` is unset and constructs `createOpenAI({ apiKey: "" })` without failing fast. The failure mode today: `POST /v2/extract` returns 200 + an id (no request-time precondition check in `apps/api/src/controllers/v2/extract.ts`), the worker consumes the job, the first LLM call 401s/errors, and the job lands as `status: "failed"` with a raw provider error (`apps/api/src/services/extract-worker.ts:102-136`). MCP users see a tool that accepts work and always fails after the fact.

**Gap 2 — `firecrawl_interact` overstates its surface.** The upstream `firecrawl-mcp@3.22.3` package (pinned by `scripts/local-firecrawl-mcp`) registers `firecrawl_interact` with a description and Zod schema advertising `code` execution with `language: "bash" | "python" | "node"`, including a worked bash example and promised stdout/stderr/exit-code returns. The local stack deliberately supports **prompt-driven interaction only**: `apps/api/src/controllers/v2/scrape-browser.ts:109-116` (`browserExecuteRequestSchema`) is a `z.strictObject` requiring `prompt`, with no `code` key and `language` limited to `z.literal("node")` — a `code` + `language: "bash"` call fails validation twice and surfaces as a 400. The runtime beneath it (`apps/browser-interaction-worker/src/protocol.mjs` `normalizeAction()`, `apps/api/src/lib/browser-runtime/protocol.ts:87-124`, `apps/browser-service/src/operations.ts`) enforces a closed 8-action vocabulary (navigate, click, hover, hover_batch, type, wait, extract, screenshot) at three layers, with explicit tool-denial hooks in the Codex decision child (`apps/browser-interaction-worker/src/deny-hook.mjs`). The MCP launcher filters only whole tools (7 disabled: agent x2, research x5); it has no mechanism to correct the code/bash/python overstatement *within* a retained tool, so the model driving the MCP is invited to use a request shape the API rejects.

**Why now:** the local runtime work (browser worker Dockerization, MCP capability filter) established a design principle — advertised capability must match configured local capability (`lat.md/operations/local-runtime.md`, "Local MCP capability filter"). These two tools are the remaining violations of that principle.

## Goals

1. `firecrawl_extract` succeeds end-to-end against the local stack: an MCP call with a schema + URL returns structured data with `status: "completed"`, using the host-side **codex-shim** LLM backend — an OpenAI-compatible `POST /v1/chat/completions` front for the operator's ChatGPT-subscription Codex CLI (no hosted Firecrawl services, no paid API key).
2. Extract failures caused by a missing or unreachable LLM backend are surfaced **early and clearly** at both layers: `scripts/local-firecrawl-mcp` probes the shim's health at MCP-session start and hides `firecrawl_extract` from `tools/list` when the probe fails, and `POST /v2/extract` returns an actionable 4xx as a backstop — never 200-then-`failed` with a raw 401.
3. `firecrawl_interact`'s advertised MCP surface matches local reality: a model reading the tool list cannot be led into sending `code`/`language: "bash"|"python"` requests that the API will 400. Prompt-driven interaction continues to work unchanged.
4. Local orchestration (`scripts/local-firecrawl`, `compose.local.yaml`, `scripts/init-local-env.sh`) documents the codex-shim backend; a fresh `init-local-env.sh` + `local-firecrawl start` yields extract **explicitly disabled** — the defined default state — until the shim is running and `OPENAI_BASE_URL` points at it.
5. `lat.md` design docs updated: `lat.md/api/http.md` "Extract" documents the LLM provider requirement (currently undocumented); `lat.md/operations/local-runtime.md` documents the new capability handling for extract and interact.
6. Measurable acceptance: the checks in the User Stories below pass against a freshly started local stack, including scrape `formats: ["json"]` through the shim (Story 1).

## Non-Goals

- No changes to the hosted/upstream `firecrawl-mcp` npm package itself; all fixes live in this repo (launcher wrapper, API, compose, docs).
- No enabling of the still-disabled upstream tools (Agent start/status, research tools) — the existing filter behavior for those is preserved.
- No expansion of the browser runtime's action vocabulary (no scroll/select/keyboard additions, and emphatically no code execution path). The 8-action prompt-driven design is intentional and stays.
- No changes to the extract pipeline's queue topology, DLQ semantics, or webhook behavior (`extract.jobs`/`extract.dlx`/`extract.dlq` stay as-is).
- No GPU provisioning, local model hosting (no Ollama), or model-performance tuning; the shim's luna/terra mapping (see Constraints) is the decided model choice, and tuning it is follow-up work beyond basic correctness.
- No changes to the hosted-cloud deployment topology (`lat.md/operations/deployment-and-ci.md` distinct-worker layout is out of scope; local harness-child topology stays).
- No parameterization of the hardcoded provider-`"openai"` call sites (`llmExtract.ts`, `completions/*`); they are routed to the shim via the `OPENAI_BASE_URL` alias instead, with `apps/api/src/lib/generic-ai.ts` unchanged (Clarifications Q5).
- Sibling-tool LLM-dependence audit (`firecrawl_parse`, search summarization, any other retained MCP tools that silently depend on LLM config) is deferred — explicitly out of scope for this epic (Clarifications Q6).

## User Stories

### Story 1: Local structured extraction works

As a Claude Code session using the local Firecrawl MCP, I want `firecrawl_extract` to return structured data from local pages, so that I can do schema-driven extraction without hosted Firecrawl or manual scrape-then-parse.

Acceptance Criteria:
- With the codex-shim running and `OPENAI_BASE_URL` pointed at it, `firecrawl_extract` (URLs + JSON schema) against a known page returns `status: "completed"` with schema-conformant data. Test fixture: designate a deterministic local page + minimal schema (avoids model-nondeterminism flake; exact fixture chosen at planning time).
- The same request via raw API (`POST http://127.0.0.1:3002/v2/extract` then `GET /v2/extract/{id}`) completes; job consumed from `extract.jobs`, no message parked in `extract.dlq`.
- Works after a cold `scripts/local-firecrawl restart` (config survives orchestration, not just a hand-edited container).
- All extract-path LLM calls route through the shim endpoint — observable as requests arriving at the shim, with no traffic to hosted OpenAI. This covers the fire-0 call sites (`analyzeSchemaAndPrompt-f0.ts`, `checkShouldExtract-f0.ts`, `url-processor-f0.ts`, `llmExtract-f0.ts`) and the reranker path that hardcodes provider `"openai"` via `apps/api/src/scraper/scrapeURL/transformers/llmExtract.ts` (see Constraints).
- Scrape with `formats: ["json"]` against the same fixture succeeds through the shim — it shares the `llmExtract.ts` plumbing and must be verified, not assumed (Clarifications Q6).

### Story 2: Misconfiguration fails fast, not late

As a local operator, I want a missing or broken LLM configuration to be visible immediately, so that I don't debug 200-then-`failed` extract jobs.

Acceptance Criteria:
- With the shim unconfigured or unreachable, **both** mechanisms fire: `firecrawl_extract` is absent from `tools/list` (launcher probes the shim's health endpoint at MCP-session start; a stale direct call returns the launcher's existing `-32601` "disabled in the local Firecrawl MCP" error), **and** `POST /v2/extract` returns a 4xx with an actionable message naming the missing/unreachable backend — the API check is the backstop for cached tool lists and non-MCP consumers.
- "Configured" means **probed alive**: env vars present but backend dead (shim down, `codex` auth broken) counts as unconfigured. Capability is evaluated at MCP-session start; mid-session config changes take effect on the next session (accepted staleness — MCP clients cache `tools/list`).
- Empty-string env vars (`OPENAI_API_KEY=""` etc., as scaffolded today) are treated as unset — no `createOpenAI({ apiKey: "" })` silently constructed. Coercion is scoped to the five LLM vars only, not central `config.ts` (Clarifications Q3).
- `scripts/local-firecrawl status` reflects whether extraction is enabled and with which provider (codex-shim), without echoing any auth material from `~/.codex`.

### Story 3: Interact tool surface tells the truth

As a Claude Code session, I want `firecrawl_interact`'s advertised description/schema to match the local prompt-driven runtime, so that I never construct `code`/`language: "bash"|"python"` requests that the API rejects with a 400.

Acceptance Criteria:
- The launcher rewrites the `firecrawl_interact` entry in `tools/list` responses — both description text and `inputSchema`: `code` mode, the Bash/Python/Node language claims, the `code`-mode usage example, and the stdout/stderr/exit-code return claims are all dropped.
- The launcher additionally intercepts stray `code`-bearing `tools/call` requests (cached tool lists) and maps them to a clear error stating the local runtime is prompt-driven only — not a bare Zod unrecognized-key 400.
- A drift guard couples the rewrite to the pinned upstream: assert `firecrawl-mcp@3.22.3` (or snapshot-test the rewritten tool entry) so a version bump fails loudly instead of silently re-advertising code execution.
- A prompt-driven `firecrawl_interact` call still succeeds end-to-end (launcher → `POST /v2/scrape/:jobId/interact` → decision worker → browser-service action).
- `firecrawl_interact_stop` continues to work unchanged.

### Story 4: Fresh environment setup is coherent

As a new operator running `scripts/init-local-env.sh` and `scripts/local-firecrawl start`, I want the LLM configuration story documented and scaffolded, so that the extract capability state after setup is deliberate rather than accidental.

Acceptance Criteria:
- After a fresh `init-local-env.sh` + `local-firecrawl start` with no shim running, extract is in the deliberate disabled state (Story 2 behavior), not silent-fail. Enablement is two documented steps: start the codex-shim, set `OPENAI_BASE_URL=http://host.docker.internal:<port>/v1`.
- `scripts/init-local-env.sh` (and `.env.example.local`) documents the LLM vars' effect: which enable extract, that empty strings mean disabled, and how to point at the shim.
- No new compose service: the codex-shim is a host-side service documented in the local runtime docs. The `api` container reaches it via `host.docker.internal` (env passthrough already exists in `docker-compose.yaml` `x-common-env` lines ~38-42; `extra_hosts: host.docker.internal:host-gateway` verified present).
- `lat.md/operations/local-runtime.md` and `lat.md/api/http.md` "Extract" updated to reflect the implemented behavior; `lat check` passes.

## Constraints

- **Local stack only.** Everything runs under docker compose (`compose.yaml` = `docker-compose.yaml` + `compose.local.yaml`); no hosted Firecrawl services (Agent, research proxy, managed browser sandbox). MCP targets the self-hosted API at `http://127.0.0.1:3002`. One deliberate exception: the codex-shim runs host-side, outside compose (it needs the host's `codex` binary and `~/.codex` auth).
- **Existing worker topology.** The extract worker is a harness child of the single `api` container (`apps/api/src/harness.ts`, `NUQ_POD_NAME=extract-worker`, health on `EXTRACT_WORKER_PORT` default 3004, not host-published). Queue infra: RabbitMQ at `NUQ_RABBITMQ_URL` (`amqp://rabbitmq:5672` in compose), Redis status via `saveExtract`/`updateExtract`, DB request ownership, MinIO artifacts. Handled failures are acked after `updateExtract(status: "failed")`; only crashes reach `extract.dlq` — preserve these semantics.
- **LLM provider selection is centralized but leaky.** `apps/api/src/lib/generic-ai.ts`: default provider is `ollama` iff `OLLAMA_BASE_URL` is set, else `openai`; `MODEL_NAME` globally overrides every call-site model name; `MODEL_EMBEDDING_NAME` overrides embeddings. BUT several extract-adjacent paths hardcode provider `"openai"` (`apps/api/src/scraper/scrapeURL/transformers/llmExtract.ts` lines 318, 321, 993-994, 1235-1237, 1347-1349, 1448-1449, 1526-1527; `apps/api/src/lib/extract/completions/analyzeSchemaAndPrompt.ts:51`; `completions/singleAnswer.ts:61-62`) — the fire-0 reranker (`reranker-f0.ts`) imports one of these. Decided handling: these call sites stay untouched and `generic-ai.ts` is not modified; `OPENAI_BASE_URL` points at the codex-shim so provider `"openai"` resolves to the local endpoint (Clarifications Q5). `SELF_HOST.md:52-61` is currently the only doc of any of this.
- **Codex CLI backend (codex-shim).** The LLM backend is the operator's ChatGPT-subscription Codex CLI: `codex-cli 0.121.0` on the host, auth in `~/.codex`. Codex CLI has no built-in OpenAI-compatible server (only experimental `app-server`/`exec-server` — not used), so a small host-side "codex-shim" service exposes `POST /v1/chat/completions` and translates each request into `codex exec --ephemeral --json`, adding `--output-schema <file>` when the request carries `response_format: json_schema`, plus `-m <model>` and `-c model_reasoning_effort=<effort>`. Model/effort mapping is shim-side config, not a `MODEL_NAME` override: small/gating call-site names (`gpt-4o-mini`-class) → `gpt-5.6-luna`, effort low; main schema-extraction names (`gpt-4.1`-class) → `gpt-5.6-terra`, effort medium. Each `codex exec` spawn costs ~2-10s; keeping gating calls on luna/low mitigates, but the upstream `firecrawl_extract` tool blocks polling until job completion, so slow inference risks MCP client timeouts (see Open Questions). Embeddings are not required: both extract rerankers (`lib/extract/reranker.ts` fire-0 path, `reranker-f0.ts`) use LLM completions via `generateCompletions`, and `getEmbeddingModel` is consumed only by `lib/ranker.ts`, which no non-test code imports — the shim returns 501 for `/v1/embeddings`. No paid API key lands in `.env`; auth stays in host `~/.codex`, and the paid-key-behind-unauthenticated-API concern reduces to subscription-quota burn, recorded as accepted risk. `local-firecrawl status` and any capability surface must never echo auth material.
- **Config schema is permissive.** All five LLM vars are `z.string().optional()` with no defaults and no empty-string coercion (`apps/api/src/config.ts:70-71`, `:313-315`). Any fail-fast behavior must handle the `""` values `init-local-env.sh` writes today.
- **The MCP launcher is a thin stdio JSON-RPC line filter.** `scripts/local-firecrawl-mcp` spawns `npx -y firecrawl-mcp@3.22.3` and filters `tools/list` results plus stale `tools/call` requests against a static `disabledLocalTools` set. It currently has no request-body rewriting, no response mutation beyond tool-list filtering, and no dynamic (config-dependent) behavior — the decided shim-health probe (extract hiding) and interact entry rewrite both extend this design. Preserve the existing pattern of keeping disabled tool names documented for future enablement.
- **Interact request contract is strict and prompt-only by design.** `browserExecuteRequestSchema` (`apps/api/src/controllers/v2/scrape-browser.ts:109-116`): required `prompt` (1..10,000 chars), `language: z.literal("node")` optional, `z.strictObject` rejects unknown keys; `InteractInput` (`apps/api/src/lib/browser-runtime/public-browser-runtime.ts:91-110`) carries prompt only. Note the JS SDK always sends `language: "node"` (`apps/js-sdk/firecrawl/src/v2/methods/scrape.ts:50-70`), so prompt mode works only because that literal was chosen — changing the literal breaks upstream-MCP prompt calls.
- **Browser runtime stays closed.** The 8-action vocabulary is validated at three layers (`apps/browser-interaction-worker/src/protocol.mjs` `normalizeAction`, `apps/api/src/lib/browser-runtime/protocol.ts:87-124`, `apps/browser-service/src/contracts.ts:259-280` / `operations.ts`), with Codex tool use denied by hook (`deny-hook.mjs`) and parent-side event rejection (`codex-runner.mjs:189-267`). Design intent per `lat.md/runtime/browser-service.md`: "Browser operations expose a compact semantic action vocabulary rather than unrestricted Playwright or CDP access." Nothing in this spec may add a code-execution path.
- **Upstream pinning.** The launcher pins `firecrawl-mcp@3.22.3`; any wrapper-side schema/description rewrite is coupled to that version's tool registration (bundled `dist/index.js`) and must be revisited on version bumps.
- **lat.md discipline.** Behavior changes require corresponding `lat.md` updates and a passing `lat check` (project CLAUDE.md post-task checklist).

## Open Questions

Prior open questions 1-10 are resolved by the decisions recorded in Clarifications (backend = codex-shim; disabled-by-default; fail-fast = both layers, probed-alive; interact = rewrite + intercept + drift guard; hardcoded-`"openai"` sites aliased via `OPENAI_BASE_URL`; luna/terra model mapping; JSON-format scrape in scope, sibling audit deferred; empty-string coercion scoped to the five LLM vars). Remaining unknowns:

1. **Shim port and health-endpoint shape.** The exact port and the health route the launcher probes (bare 200 vs a capability payload) are unpicked.
2. **Shim process supervision.** Systemd user service vs managed by `scripts/local-firecrawl` (which otherwise only drives compose) — affects the enablement docs and `status` reporting.
3. **Shim mapping key.** Map by incoming model name (`gpt-4o-mini`-class → luna, `gpt-4.1`-class → terra) or a static two-tier config? The tiers are decided; the keying mechanism is not.
4. **E2E pipeline beyond the first LLM call is unexercised self-hosted** (DB/Redis/MinIO interactions in the fire-0 pipeline). A de-risking spike — one full extract through the shim — is recommended before beads are sized.
5. **MCP client timeout budget for long extracts.** Upstream `firecrawl_extract` blocks polling until completion; with ~2-10s per `codex exec` spawn across gating + per-URL + rerank calls, worst-case latency vs client timeout is unquantified.
6. **Should `language` stay `z.literal("node")` in `browserExecuteRequestSchema`?** It exists only because the upstream SDK always sends `language: "node"`. Keep as-is, widen to accept-and-ignore, or strip in the launcher — low stakes, decide during Story 3 work.
